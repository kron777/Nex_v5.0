--- Q3: IS "SAME THING AGAIN" A RECORDED FACT? ---

Short answer: Yes — via three separate, independent, EXACT (never fuzzy
or NLP-similarity-based) mechanisms that genuinely exist and work as
designed — but NONE of the three is the mechanism that actually carried
"Royal Family" into this incident, which has NO identity-tracking of any
kind, exact or fuzzy, at all.

fountain_events itself (the base fire log) has NO stable topic/subject
identifier field — its schema is exactly: id, ts, thought, droplet,
readiness, hot_branch, word_count, anchor_belief_id. Checked directly:
anchor_belief_id was NULL for every one of the 15 fires in this incident
(and for all 58 historical Royal-Family hits found in Step 0). droplet is
a text-DERIVED slug (via theory_x/stage6_fountain/condenser.py) that
changes with every rewording — confirmed different on every one of the
15 fires, so it is not a stable key. hot_branch is a topical-flavour
label picked per-fire, confirmed to vary continuously across all 15 fires
(never once a consistent "this is the same group" tag).

But three OTHER, real, exact mechanisms do exist and were directly
verified:

1. fountain_prompt_blocks (dynamic.db — NOT dropped on restart, by
   explicit design; its own code comment says it was built in round 37
   specifically "because retrospective questions couldn't be answered
   before"). Stores a content HASH per prompt block per fire. Queried
   directly for this incident: block ordinal 1 (the literal quoted feed
   item, e.g. '"Our Most Aligned Model Yet"') has the IDENTICAL hash
   ba0af2ca977c across fires 3265, 3267, 3273, 3276, and 3282 — direct,
   checkable proof the exact same source text was reused verbatim, not
   independently re-worded by the model from a fresh source each time.

2. WorldBridgeSelector (theory_x/world_bridge/selector.py — the frozen
   "selector.py," read-only, 476 lines, class WorldBridgeSelector)
   maintains an in-memory deque of up to 15 exact fingerprint strings
   (_recent_fingerprints; fingerprint = the full formatted event text,
   title+body) and actively drops (_dedup method, lines 426-442) any
   event whose fingerprint was already shown recently. This is real,
   working, exact-string dedup, confirmed by reading the method directly
   — not fuzzy similarity. (Checked and ruled OUT as this incident's
   source — see below — but it is real and does work for what it does
   cover.)

3. GrooveSpotter (theory_x/diversity/groove.py) fingerprints the top
   repeating n-gram/template per scan and refuses to re-log it while
   unchanged (_last_ngram_pattern / _last_template_ids, exact-match
   fingerprints, not fuzzy) — this is the exact mechanism that DID trip
   on "aligned model" during this incident (Step 0, Q2).

So where did "Royal Family" actually come from, mechanistically, given
none of the THREE tracked/logged retrieval slots (seed=koans/philosophy;
own_sense=recent precipitated_from_sense headlines; the wide-mode
{item}=the one explicit quoted feed headline) ever contained it during
this window (verified directly: queried fountain_retrieval_log's
own_sense and seed rows for fire 3265 and the precipitated_from_sense
pool for the surrounding hours — "Royal Family" appears in NONE of them)?
Traced directly in generator.py's Layer 4 "SOCIAL" block
(lines ~3616-3651), which runs unconditionally on every fire with ZERO
dedup of any kind:

  SELECT payload FROM sense_events WHERE stream = 'external.other_mind'
  ORDER BY timestamp DESC LIMIT <_soc_n>

This block was ACTIVE during this run — its header text ("SOCIAL: another
mind has been responding...") is present at prompt-block ordinal 3 in
every one of the 15 fires' fountain_prompt_blocks rows, directly checked.
sense.db's external.other_mind stream (a running conversational-partner
simulation, not Jon) contains a message at 2026-11-10 20:56:27: "That's
fascinating how you've noticed the Royal Family's direct engagement with
honoring veterans. What insights do you have on how this might impact
future mil[itary]..." Because this SELECT has no staleness check and no
dedup (unlike WorldBridge's separate consumer of the same underlying
table, which DOES dedup — mechanism #2 above), the same payload is
eligible to be re-read fire after fire for as long as nothing newer lands
on that one specific stream. This channel has NO identity tracking of any
kind — not an id, not a hash, not a fingerprint — it is a bare "most
recent N rows" read, re-executed from scratch every single fire. That gap
— not a missing paraphrase-similarity detector — is the real, specific
reason "Royal Family" was never caught by anything: it never had to be
RECOGNIZED as a repeat by any detector, because the mechanism that
surfaced it doesn't check for repeats at all, by design (its own comment
calls it an experimental, "env-gated, default OFF" layer testing a
different hypothesis entirely — "responsive CONTACT," not repetition
safety).

One more, independent, pre-existing, NAMED instance of this exact failure
class already lives in the code, discovered while tracing this:
_build_recent_striking_block's "CARRY-SIDE TOPIC GATE"
(NEX5_CARRY_TOPIC_GATE, default OFF; generator.py ~line 2648) was built
