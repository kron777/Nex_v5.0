ANSWER: within ONE fire's _build_prompt call, the SOCIAL block (3722) runs
BEFORE the call to _build_recent_striking_block (3861) -- so by the time
the gate's own method runs, SOCIAL's text is already sitting in
prompt_parts for the CURRENT fire. But the gate itself never reads
prompt_parts, never reads the current fire's input blocks at all --
_recent_fire_topic_terms (2613) only queries fountain_events, i.e. PAST
fire OUTPUT, several fires old by the time it's read. So the ordering
within one fire is actually irrelevant to the gap: the gate is structurally
blind to every current-fire INPUT channel, SOCIAL included, no matter
where in the sequence it sits. Fixing the ordering would do nothing; seeing
the input blocks directly (Beam's ruling) is the only thing that would.

TASK 3 -- SOCIAL MADE VISIBLE TO THE GATE'S ROLLING HISTORY
=============================================================================

NEX5_CARRY_TOPIC_GATE's OWN _recent_fire_topic_terms (line 2613) is
UNCHANGED -- still reads only fountain_events.thought, nothing added to it,
nothing routed into it. Per the brief: "Don't change what SOCIAL itself
reads or does" and "Don't flip NEX5_CARRY_TOPIC_GATE" -- both held.

Instead, a SEPARATE, shadow-only per-process history was added:

  self._topic_gate_shadow_social_history = deque(maxlen=_CARRY_TOPIC_WINDOW)
  (generator.py, in __init__, next to the existing self._social_n init)

Every fire, _record_topic_gate_shadow appends that fire's SOCIAL text (even
"" when SOCIAL contributed nothing) to this deque -- on purpose: SOCIAL
repeating the same text fire after fire for lack of anything newer IS the
signal this exists to surface, so a flat/unchanging read must still show up
in the history, not be silently skipped. It then recomputes
_dominant_topic_terms over (the 40 trailing fire-outputs) + (this SOCIAL
history) combined -- rolling_terms_with_social. This is the "one level up"
view Beam's ruling asked for: SOCIAL's contribution now sits in the SAME
kind of rolling corpus the gate's own logic already understands, without
touching SOCIAL's read path or the gate's own default.

Caveat found and reported honestly: because the window is 40 FIRES but
SOCIAL only changes every ~5-15 fires' worth of wall-clock time (it reads
the single latest external.other_mind row, which arrives far less often
than fountain fires do), SOCIAL's own text ends up appearing MANY times in
its own 40-entry history for each time it actually changes. This inflates
SOCIAL's own words' apparent document-frequency independent of whether the
fountain's real output is doing anything repetitive -- a genuine confound,
discussed further in Task 5.

detour to hide:

TASK 6 -- RECOMMENDATION (not implemented, per the brief)
=============================================================================

Hard suppression, down-weighting, or suppress-with-cooldown? SUPPRESS-WITH-
COOLDOWN, keyed on EXACT repeated identity, not on a lexical overlap score.

Why not hard suppression: this investigation's own data (Task 5) shows no
lexical overlap design tried here reliably distinguishes the real incident
from ordinary chatty content -- using any of them to hard-block a fire
outright risks blocking normal, healthy content (the baseline window would
have been blocked under Designs 2 and 3 at every single fire). Hard
suppression on an unreliable signal is worse than doing nothing.

Why not plain down-weighting: down-weighting (reducing salience/budget
competitiveness without ever fully stopping repetition) assumes a
CONTINUOUS, well-calibrated signal to weight BY -- which is exactly what
this round's lexical attempts failed to produce. Down-weighting against
a noisy or inverted signal just adds noise to generation without fixing
anything, and (per groove_facts.txt's Q1 budget-replay finding) nothing
resembling a working cost/budget mechanism exists on this path today to
hook a weight into anyway.

Why suppress-with-cooldown: it is the ONE mechanism in this codebase
already PROVEN to work end to end on a signal of comparable exactness --
groove.py's own cooldown, keyed on exact/near-exact n-gram and template
matches (not fuzzy lexical overlap), already fires, already writes a real
suppression window, and groove_facts.txt independently confirmed it
actually blocked a real fire during the incident (fire 3283, matched_
pattern='aligned model'). The gap groove_facts.txt found was never "this
mechanism doesn't work" -- it was "this mechanism never got to see the
content that needed it" (the Royal-Family half never crystallized into a
belief, so GrooveSpotter never saw it). The fix implied by this round's own
data is NOT a new fuzzy-overlap gate at fire-assembly; it is the SAME
proven suppress-with-cooldown shape, keyed on the cleaner EXACT signal this
round surfaced (focal_item repetition, or the prompt-block content hash
already recorded in fountain_prompt_blocks), applied one level up so every
input channel -- SOCIAL included -- is visible to it, exactly as Beam's
ruling specified. A real threshold is already suggested by the data: 60%
(incident) vs. a 13% ceiling (baseline, including a legitimate real-news
recurrence) leaves wide room; something in the 25-40% band -- notably
overlapping the SAME 0.30 already used elsewhere in this file for an
analogous purpose (NEX5_FOCUS_ROTATE) -- is a reasonable starting point for
the later prompt that actually wires this.

This recommendation is NOT implemented in this round -- no suppression,
weighting, or cooldown logic was added anywhere; topic_gate_shadow_log
remains pure observation, and focal_item's cleaner signal was found and
measured, not wired into anything live.
