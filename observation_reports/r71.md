## C5.2 — the defect: a gate scoped to the batch, not the window

`b20ac35`'s commit message states the intent precisely:

> *"single-word entities now require 3+ mentions **in the lookback window** before opening"*

**The code does not count over the lookback window.** `_entity_counts` is built from `rows`
(`signal_to_problem.py:289-299`) — the `LIMIT 20` fetch, filtered `actioned_at IS NULL`:

```python
for _s in rows:                      # <- the tick's batch, not the 6h window
    _entity_counts[_e.strip().lower()] += 1
...
_min_mentions = 3 if (entity and " " not in entity.strip()) else 2
if (... _entity_counts.get(entity.strip().lower(), 0) < _min_mentions):
    b_cx.execute("UPDATE signals SET actioned_at=? WHERE id=?", ...)   # consumed
```

**Every row is marked `actioned` whether or not it opens a problem**, so the unactioned pool
is drained every `TICK_SECONDS = 120`. At 66/day the pool refills with **~0.09 rows per
tick**. The batch therefore almost always holds one row, and a one-row batch can never show
an entity three times.

**Reconstructed from `actioned_at` — the ticks are directly observable:**

| | |
|---|---|
| ticks reconstructed (227 signals) | **149** |
| ticks holding exactly 1 signal | **110 (73.8%)** |
| **max same-entity count reached, ever** | **2** |
| **ticks clearing the ≥3 single-word bar** | **0 of 149** |

**The bar is unreachable by construction.** `Bitcoin` alone produced **59** signals in 3.1
days and opened nothing.
