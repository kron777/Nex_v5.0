## B. The prompt block manifest

### B.1 Design — reported before the code, and it changed twice on evidence

**First finding, OBSERVED: partial instrumentation already existed and nobody used it.** `fountain_retrieval_log` records `(fire_id, belief_id, slot, rank, boost_value, ts)`. But:

- it covers **only three slots** — `seed`, `own_sense`, `spectrum`
- it reaches **57% of fires** (300 of 530 in 24h)
- it holds **1 day** of data, because `generator.py:450` does **`DROP TABLE IF EXISTS fountain_retrieval_log` on every startup**

That last point is the whole problem. **A log destroyed on every restart can never answer a retrospective question**, which is exactly why R31, R32 and R33 each had to live-sample `/tmp/nex5_last_prompt.log`. It also misses every block that is not belief-sourced: the exemplar block (reads `fountain_events`), the momentum carry, `self_narrative`, favourites, the mode template, and the focal item — i.e. **all six carriers identified in R33's C4**.

**Second finding, OBSERVED: content-addressing does not work here.** I intended to store each block's text once, keyed by hash. Measured across 8 sampled prompts, 131 blocks:

```
distinct block hashes : 116  ->  dedup ratio only 1.13x
stored-once bytes     : 91% of raw
```

Most blocks embed a changing timestamp or count (`"274 min ago"`, `"Time: 10:35"`, `"Beliefs held: 53189"`), so almost nothing repeats. Full-text storage would cost ~2.8 MB/day for near-zero sharing. **Rejected on the measurement.**

**Shipped design:** one row per block per fire —

| column | purpose |
|---|---|
| `fire_id`, `ordinal` | which fire, and the block's position in the prompt |
| `block` | first 48 chars of the block's first line — the block's identity |
| `hash` | blake2b-64 of full content — makes exact repeats countable across fires |
| `n_chars` | length |
| `prefix` | **first 96 chars, newlines flattened** — makes a preamble-style contaminant findable after the fact, which was the actual R31–33 case |
| `ts` | — |

Measured on a real 5,920-char prompt: **16 blocks**.

### B.2 Storage cost and the reaper

~110 B/row × 16 blocks = **~1.8 KiB/fire** → **~930 KiB/day** at 530 fires/day → ~330 MiB/year.

**Revised on first live data — OBSERVED.** The first post-restart fire was DRIFT mode and produced **25 rows**, not 16: DRIFT assembles more, shorter blocks than ARGUE/EXPLAIN. Block count is therefore mode-dependent, roughly **16–25/fire**, so the realistic upper bound is **~2.8 KiB/fire → ~1.4 MiB/day → ~520 MiB/year**. Still bounded, and the reaper below caps it regardless. The true mean needs 24 h across the mode mix.

**It does need a reaper and here it is: 30-day retention**, `DELETE FROM fountain_prompt_blocks WHERE ts < now-30d`, run **once per process start** — never on the fire path. Steady state **~27–43 MiB**. This matches the retention pattern already used for `gate_decisions`/`throw_net_sessions` (`9ff1f4c`).

I could have made it reaper-free by storing hash-only, but then it cannot answer the one question it exists to answer. The prefix is the point; the reaper is its price.

### B.3 Fail-safe — OBSERVED

Three layers, because this sits on the fire path:

1. `_prompt_block_manifest` is a `@staticmethod` **pure function** — no I/O, no state.
2. Its call site wraps it: any exception sets `self._last_prompt_blocks = []` and the fire proceeds.
3. The write runs **after the fire row already exists**, wrapped, reporting to `error_channel`.

Tested against `None`, `''`, `'\n\n\n'`, `int`, and a bare `object()`. The three string cases return cleanly (0 blocks); the two non-string cases raise `TypeError` **inside the caller's try**, which is unreachable in practice since `_prompt_text` is always `"\n".join(...)`.

### B.4 Records, does not alter — OBSERVED

- `_prompt_text` is assembled, **then** hashed, **then** returned unmodified (`generator.py:2771`, `2778`, `2782`).
- `grep` for `fountain_prompt_blocks` finds **only** CREATE/INDEX/INSERT/DELETE. **No readers.**
- The table is **not** dropped on startup — deliberately, unlike its predecessor.

### B.5 One restart, three changes — and why that is not batching

The VACUUM, the manifest, and R33's B1 activation all landed on 08:44:38Z. **This is acceptable here for one reason only: not one of the three has a behavioural endpoint.** None can move the R32 measurement, subject fidelity, STRIKING, or crystallization. There is no attribution to confound because there is nothing to attribute.

**A future round must not read this as precedent for batching.** R27+R29 were batched on one restart and R31 spent effort untangling them; that was batching, because both had endpoints. This is not.

### B.6 Recommendation on persisted reject reasons

**It belongs with the fidelity work, not this restart.** `_quality_check` returns `(bool, reason)` and nothing stores it. Persisting the reason is inert in the same sense as the manifest — but the *reason it is wanted* is to measure the engagement gate, which is the EXPLAIN change's endpoint. Shipping it now would mean the instrument and its subject arrive on separate restarts with an R32 read in between; shipping it **with** the EXPLAIN work gives a clean before/after in one series. **Recommend: defer to the fidelity/EXPLAIN round.** It is cheap either way.

## C. The failed boots — mechanism, not fixed

### C.1 What the warning is — OBSERVED

`nex_keepalive.sh:86`. After `launch_nex`, the script does `sleep 25` and then:

```bash
is_alive() { ss -tlnp | grep -q ":${PORT} " && kill -0 "${NEX_PID}"; }
```

If that fails it prints `WARNING: NEX did not come up on first launch`.

**It does not retry on the warning.** The warning is purely informational. Control falls into `while true; do sleep 30; if ! is_alive; then ...RESTART #N...`. So the real decision happens **30 seconds later**.

### C.2 What actually failed on those three occasions — nothing — OBSERVED

**No `RESTART #` event follows any of the three warnings.** The next journal line in each case is the next Stop/Start, hours later. That means `is_alive` returned true at the first 30 s loop check: NEX came up somewhere between 25 s and 55 s.

Fire-gap evidence confirms nothing was lost:

| warning | gap in fires |
|---|---|
| 08-04 12:20:25 | 6.7 min |
| 08-06 09:17:33 | 4.1 min |
| 08-07 16:19:44 | 5.5 min |

A clean restart costs 3–4 min to first fire. These are **normal restart gaps**.

**The mechanism is a marginal timeout, not a failure.** Boot lands within a few seconds of the 25 s deadline: this round's restart logged `launched 10:44:42 → confirmed up 10:45:08` = **26 s**, and R32's was **exactly 25 s**. A machine reboot — cold page cache, other services contending — pushes it over. The warning fires; the system is fine 30 s later.

**Where the record runs out:** `journalctl --user` retains from **2026-07-17 03:58**. Anything earlier is gone. `/tmp/nex5_soak.log` is wiped on reboot, so the soak log the warning points you to *does not survive the reboot that produced it* — the warning names an already-destroyed artefact.

### C.3 Is state lost or corrupted? — OBSERVED, no

- Databases are WAL; an unclean stop replays the WAL on next open. `integrity_check` after today's VACUUM returned **ok** across a database that has survived all five reboots.
- The keepalive's `flock` is on `/tmp/nex5_keepalive.lock`, and `/tmp` is cleared on reboot, so a stale lock cannot survive one. It has a 10×1 s retry for the restart handoff race (`session 47` fix).
- No partial writes: writers go through `substrate/writer.py`, and the only `substrate.writer ERROR` entries in the soak log are unrelated to boot.

### C.4 Were the clean boots different, or luck? — REASONED: essentially luck

Two boots cleared 25 s and three did not. Given measured boot times of 25 s and 26 s on a *warm* system, the distribution straddles the threshold. I found no configuration or ordering difference between them. **This is a coin-flip against a too-tight deadline, not two populations.** Raising the sleep to 45 s would silence all five; I did not change it, per instruction.

### C.5 The restart/deploy ledger — designed, not built

`journalctl --user` is retention-bounded (currently 2026-07-17) and will lose the history R36 needed. Design:

- **File:** `journal/DEPLOY_LEDGER.tsv`, append-only, in the repo so it is versioned and survives.
- **Columns:** `ts_utc`, `event` (`stop`/`start`/`vacuum`/`boot`), `commit_sha`, `service_pid`, `note`.
- **Written by:** `nex_keepalive.sh` on start (one line), plus a manual line per round.
- **Cost:** ~100 B per restart, ~40 restarts/month → 4 KB/month. **Never needs a reaper.**
- **Backfill:** the current `journalctl` window (2026-07-17 →) can be imported once before it ages out. Everything before is unrecoverable.

Not built — it touches `nex_keepalive.sh`, which is the launch path, and this round's remit was things that do not touch behaviour.

## D. Does the groove-filter claim survive if the scorer is the upstream cause?

**They compose; they do not compete.** The scorer decides *which* fires enter the top-10 pool; the groove filter decided *which of those survived to be sampled*. A scorer that over-selects near-duplicates and a filter that removes everything except the duplicate are complementary mechanisms acting at different stages, and the observed 10-of-10 mono-culture is better explained by both than by either — so confirming the scorer as upstream cause would *raise*, not lower, my confidence in the filter claim.
