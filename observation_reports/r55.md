### B.2 The mechanism test — **NOT supported** — OBSERVED

R54 hypothesised that relevance raises output length *because it supplies longer priors that the model echoes*. The instrumentation added this round tests it directly (n=33 fires carrying prior lengths):

```
mean chars of the priors each arm supplied:
   recency   124.5
   relevance 200.8      delta +76.3   <- the premise holds: priors ARE longer

paired r(delta prior length, delta output length) = +0.086   <- but almost no relationship
```

**The priors really are 61% longer, and that barely predicts output length.** At r = +0.086 the echo hypothesis explains under 1% of the variance. **So if the `too_long` rise is real, it is not simple length echo** — and the obvious cheap fix (truncate the priors) would not address it.

### B.3 Shippable alone, or paired gate change? — **UNDECIDED, and honestly so**

The round asked this to be settled. **It cannot be, on n=73.** What can be said:

- The effect is **directionally consistent across two runs** and would, if real at +6.9 pp, push `too_long` from 0.137 to 0.205 — a **50% relative rise in rejections at the first crystallization gate**, which would cut crystallization rather than raise it.
- Its proposed mechanism is falsified, so **the paired gate change nobody has designed yet cannot be designed from this data** — we do not know what is driving the length.
- **Therefore relevance retrieval is not shippable on current evidence**, not because the risk is proven but because a plausible harm is unresolved and its cause is unknown.

## C. The verdict on the direction — **CANNOT ANSWER**

**C.1 — does relevance retrieval improve generated thought by a margin worth shipping? Unanswerable at n=73 against a required 615.** Direction is mildly positive on `on_subject` (+0.041, CI spanning zero). **I will not convert "directionally positive, twice" into a verdict; that is exactly the inference this whole audit exists to avoid.**

**C.2 — retrieval problem or model-capacity problem?** — **REASONED, and I can only narrow it, not settle it.** One observation does bear on it: `novelty_F2` is **1.000 in both arms** and the delta is −0.0001. The 3B model produces text that is maximally novel against the rolling reference regardless of what it is given — it is not echoing its priors in either arm (consistent with §B.2's r = +0.086). **That is weak evidence for the capacity side:** a model that barely conditions on retrieved context will not benefit much from better context. But `on_subject` did move +4 pp, so it is not *ignoring* the priors either. **Distinguishing these properly needs the same run at a larger model, which is a second experiment, not a corollary of this one.**

**C.3 — n/a** (C.1 is not YES).

**What it would actually take, priced:**

| option | cost | verdict |
|---|---|---|
| run against live NEX | ~6 h at 22 → 4–14 fires/h + timeouts | **rejected — measured this round** |
| **stop the fountain, run, restart** | ~6 h downtime, one restart | **viable**; the restart also activates R53's staged pool fix, which must be declared in the ledger |

| accept n≈150 over several nights at concurrency 1 | still underpowered | not worth it |

**My recommendation: the second instance.** It is the only option that neither degrades the system nor forces a restart into R54's window.

## D. Honest limits

R54's limit stands and now matters more: **the harness uses a reduced prompt** (mode template + item + belief block, not production's ~15 blocks), so it measures a differential that may not transfer. **How much should that discount a positive result?** Substantially — the production prompt carries ~3.3 KiB across ~15 blocks, so the belief block is a smaller share of the context there than here. **The harness therefore likely *overstates* the effect of swapping it.** A positive result here would be an upper bound, and a null here — which is what we have twice — is correspondingly harder to dismiss.
