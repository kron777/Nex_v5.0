## 1.4 — why that breaks the test specifically, and which way it breaks

The test splits the corpus into two time-ordered halves and calibrates, on each,
θ = the smallest even % at which **FPR ≤ 1%**. That calibration assumes the corpus contains
**no real convergences** — every firing is counted as a false positive.

| | half A (08-09 → 08-15 10:37) | half B (08-15 10:41 → 08-21) |
|---|---|---|
| `societal` DF | **1.0%** | **7.3%** |
| `advancements` DF | **2.5%** | **16.0%** |

**Both convergences land almost entirely in half B.** maxDF* fires on them, those firings
are scored as false positives, half B's FPR is inflated, and **θ_B is pushed up to suppress
them.** θ_A is not.

**So the failure is directional, not random: the contamination manufactures
|θ_A − θ_B| > 4 pp — a spurious FAIL — and routes the decision into Branch B.** Branch B
then schedules the B=400 stability test at **1,200 documents**, on evidence that measured a
news cycle. **Running the test today does not risk an ambiguous answer; it risks a
confident wrong one, in the expensive direction.**

# §2 — THE BATCH-VS-WINDOW SCOPE FIX (pre-registered)

**Everything below §2.1 was written before the file was edited.** This change goes live on
the next auto-restart — **there is no staging** ([[nex5-staging-is-not-durable]]) — so the
statement of what counts as success and failure has to exist first.

## 2.1 — the exact change

**File:** `theory_x/signals/signal_to_problem.py`, one block, lines 285–299.

**Now** — the recurrence counter is built from `rows`, the tick's `LIMIT 20` fetch, which is
filtered `actioned_at IS NULL`:

```python
_entity_counts = _Counter()
if os.environ.get("NEX5_SIG_QUALITY") == "1":
    for _s in rows:                      # <- the tick's batch
        ...
        _entity_counts[_e.strip().lower()] += 1
```

**After** — built from every promotable signal in the lookback window, **regardless of
`actioned_at`**:

```python
_entity_counts = _Counter()
if os.environ.get("NEX5_SIG_QUALITY") == "1":
    _wrows = b_cx.execute(
        f"SELECT payload FROM signals "
        f"WHERE detected_at > ? AND signal_type IN ({type_placeholders})",
        (cutoff, *_PROMOTABLE_TYPES)
    ).fetchall()
    for _s in _wrows:                    # <- the whole 6h window
        ...
        _entity_counts[_e.strip().lower()] += 1
```

**Nothing else moves.** `_min_mentions` stays 3 for single-word and 2 for multi-word. The
`_VAGUE_ENTITY_WORDS` blocklist, the `prose_stats` corpus check, the 7-day dedupe, the 5/day
cap and `MIN_CONFIDENCE` are all untouched. **The bar is not lowered — it is applied to the
population the commit that introduced it already claimed to apply it to** (`b20ac35`:
*"3+ mentions in the lookback window"*).

**Cost:** one extra `SELECT` per 120 s tick over a 6 h window — **~18 rows** at current
volume.

**Why `actioned_at` must not be filtered:** that filter is the defect. Rows are marked
actioned whether or not they open a problem, so filtering on it means the counter can only
ever see rows nothing has looked at yet — which, at 0.09 arrivals per tick, is one row.

## 2.2 — `4_branch`: **folded in, not deferred**

`signal_type` is built dynamically as `f"{len(branches)}_branch"` (`detectors.py:87`), so
`4_branch` appears whenever an entity spans four branches — **first seen 2026-08-17**, as
branch count grew. It is **absent from `_PROMOTABLE_TYPES` and has never opened a problem.**

**Folding it in, because the exclusion is an artifact rather than a decision:**

- **Strictly stronger than a type already promoted.** `3_branch` (conf 0.90) is promotable;
  `4_branch` is conf **0.95** and more corroborated. No reading makes 3 admissible and 4 not.
- **The sibling check from R71 §B2 carries over unchanged.** `4_branch` has no clause in
  `_compose_title`, so it takes the entity fallback — `Signal: investigate '{entity}'` —
  which means it faces the *full* R27 quality gate, blocklist and corpus check included.
  It is strictly more filtered than the burst types ever were.
- **It cannot flood.** 3 signals in 4 days ≈ **0.75/day** against a 5/day cap.

**Deferring it would cost a whole round to add one string to a frozenset this round already
edits.**

**The residual gap, stated rather than fixed:** `5_branch` will appear the same silent way
once an entity spans five branches. **I am not adding types that have never been observed** —
that ships promotion behaviour I cannot check against real data. Instead the change logs a
warning when an `N_branch` type shows up that the set does not contain, which converts the
next instance from a silent starvation into a visible line. **Tripwire: if that warning ever
fires, extend the set.**

## 2.4 — what proves it wrong, or worse

**Any one of these is a revert, no discussion:**

| # | trip | reading |
|---|---|---|
| 1 | **any problem opens on an entity in `_VAGUE_ENTITY_WORDS`** | over-match — the R26 sibling check failed and the quality gate is not holding |
| 2 | **> 25 entity-named problems in 7 days** (> 3.5/day, approaching the cap) | the window bar is too loose; recurrence is being counted where it should not be |
| 3 | **the 5/day cap is hit on ≥ 3 of 7 days** | the queue is being crowded again — the R71 harm, re-created with different titles |
| 4 | **non-closed queue depth > 10** | problems opening faster than they resolve; R69's baseline was exactly 1 |
| 5 | **0 entity-named problems after 48 h** | **the fix is wrong** — the batch/window scope was not the binding constraint and the diagnosis in R71 §C5 is incomplete. Revert and look elsewhere. |

**Trip 5 is the honest one.** R71 §C5 argued the scope defect is *the* blocker on the
strength of a counterfactual replay, not a live run. **If entity problems still do not open,
that argument was wrong** and the next round starts from the `prose_stats` corpus check and
the dedupe, not from here.
